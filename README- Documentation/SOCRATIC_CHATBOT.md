# Socratic Chatbot Architecture and Rules

This document explains how the Socratic tutor currently works in the codebase, including:

- end-to-end request flow,
- mastery integration (BKT),
- retrieval grounding (RAG),
- tone and frustration adaptation,
- strict output constraints used for model responses,
- policy gates that decide whether chat updates mastery.

It reflects `socratic_tutor.py` and `main.py` as they run today.

---

## 1) What this chatbot is (and is not)

The tutor is a **state-aware Socratic hint generator**, not a direct answer generator.

- It uses:
  - a shared BKT learner model (`ScienceBKT`),
  - a local syllabus retrieval layer (`retrieve_context`),
  - an LLM call (Groq via `langchain_groq`),
  - structured JSON outputs.
- It is designed to:
  - give a short corrective/scaffolded hint,
  - ask one next-step question,
  - score learner interaction (`interaction_score`) for optional dialogue-driven BKT updates.
- It is **not** a free-form QA bot that dumps full solutions.

---

## 2) High-level request flow

### A) API layer (`main.py`)

Chat requests arrive through:

- `POST /tutor/hint` (explicit topic provided),
- `POST /tutor/hint-auto-topic` (topic optional; infer if missing).

The API:

1. passes request fields to `generate_socratic_hint(...)` or `generate_socratic_hint_auto_topic(...)`,
2. records successful chat turns in local runtime stores,
3. appends interaction logs (`interaction_logs.json`),
4. appends numeric interaction signals for analytics velocity checks.

### B) Tutor core (`socratic_tutor.py`)

For each turn, the tutor:

1. reads current mastery `P(L)` for `(user_id, topic_id)`,
2. retrieves textbook chunks for that topic,
3. builds mode-specific system instructions (scaffold / balanced / nudge),
4. injects conversation history and frustration guidance,
5. invokes LLM with strict JSON output contract,
6. parses `hint_text` + `interaction_score`,
7. conditionally updates BKT using policy gate (`strict` / `quiz_only` / `legacy`),
8. returns full structured response payload.

---

## 3) Shared learner state (BKT integration)

The chatbot and assessment endpoints share the same BKT engine instance:

- `get_shared_bkt_engine()` returns one process-wide `ScienceBKT`.
- State key is `(user_id, skill_name/topic_id)`.
- This gives one mastery trajectory per learner per topic.

### Chat-driven BKT policy (`TUTOR_BKT_POLICY`)

The environment variable controls whether chat can update mastery:

- `quiz_only` (default):
  - chat never updates BKT,
  - only `/api/v1/assessment-submit` updates mastery.
- `strict`:
  - `interaction_score >= 0.78` -> BKT label `1`,
  - `interaction_score <= 0.42` -> BKT label `0`,
  - otherwise skip update (`dialogue_score_ambiguous_bkt_skipped`).
- `legacy`:
  - uses discounted mapping (`score * 0.5 >= 0.25` -> label `1`),
  - intentionally lenient; can over-inflate mastery.

### Why this matters

`interaction_score` is generated by the model, so policy gating prevents noisy mid-confidence scores from changing mastery too aggressively.

---

## 4) Hint mode selection by mastery

Before LLM call, tutor chooses a pedagogical mode from current `P(L)`:

- `scaffold` if `P(L) < 0.5`
- `balanced` if `0.5 <= P(L) <= 0.8`
- `nudge` if `P(L) > 0.8`

Mode influences prompting style:

- **Scaffold:** concrete everyday analogies + more guided explanation.
- **Balanced:** correction-first with compact explanation.
- **Nudge:** counterfactual/probing prompt for transfer.

---

## 5) Frustration-aware tone adaptation

Frustration cues come from `POST /api/v1/engagement/frustration-cue`.

`upsert_frustration_signal(...)` clamps score to `[0,1]` and maps levels:

- `low` `< 0.34`
- `medium` `0.34..0.66`
- `high` `> 0.66`

Tutor then injects tone guidance into system prompt:

- high frustration -> very patient, shorter steps, gentle correction,
- medium -> supportive and clear,
- low -> standard warm Socratic pacing.

Important: frustration signals affect **tone**, not direct BKT updates.

---

## 6) Retrieval grounding constraints (RAG)

The system prompt enforces textbook grounding:

- science authority is retrieved excerpts from local textbook context (`science G-6 E (1).pdf` chunks),
- if student conflicts with source, correct using retrieved definitions,
- avoid unsupported references to figures/tables/examples unless briefly explained in plain language.

This is a grounding constraint to reduce hallucination and keep domain consistency.

---

## 7) Response constraints and generation rules

The prompt requires strict behavior. Core rules include:

1. **No direct full solutions**
   - avoid giving complete final answer/fully worked result.

2. **Correction-first protocol**
   - validation -> gentle correction (with analogy/plain contrast) -> exactly one follow-up question.

3. **Conversation continuity**
   - treat latest student message as likely reply to previous tutor question.
   - explicitly acknowledge or quote student wording.

4. **Repetition control**
   - avoid repeatedly opening with the same phrase.

5. **Brevity**
   - hint should be concise (target <= 120 words).

6. **Interaction score calibration**
   - wrong/confused usually <= 0.35,
   - major misconception <= 0.25,
   - clearly correct >= 0.78.

7. **Mandatory JSON-only format**
   - output exactly:
     - `hint_text` (string),
     - `interaction_score` (number).
   - no markdown fences, no extra keys/comments.

---

## 8) Analogy strategy used in prompting

You asked for analogy-driven tutoring behavior. This is encoded in prompt mode blocks:

- In low mastery (`scaffold`), tutor is explicitly instructed to use everyday analogies such as:
  - water pipes,
  - highways,
  - kitchens,
  - batteries,
  - cooking.
- In balanced mode, analogy stays compact and corrective.
- In nudge mode, analogies are lighter and focus shifts to "what if variable changes?" counterfactual transfer.

This is not random style drift; it is a deliberate, mode-conditioned instruction strategy.

---

## 9) Topic inference behavior (`/tutor/hint-auto-topic`)

If `topic_id` is absent:

- tutor calls `infer_topic_id_from_question(...)`,
- uses keyword overlap from `_TOPIC_KEYWORDS` + curated aliases,
- includes lightweight fuzzy prefix matching,
- falls back to `G6_S1_ORG_CHARS` if nothing matches.

Response includes:

- `topic_id_inferred` (bool),
- `topic_id_resolved` (final topic used).

---

## 10) Failure handling and safe fallback

If LLM output is malformed:

- parser tries JSON decode,
- one automatic retry is attempted for empty/malformed outputs,
- if still broken, user gets safe fallback hint text:
  - "I had trouble reading the tutor response just now. Please try sending your message again."
- BKT update is skipped when score is missing/invalid.

This prevents runtime crashes and prevents accidental mastery corruption from malformed responses.

---

## 11) Runtime memory and persistence around chatbot

On successful chat turns, API stores:

- structured chat turn history (in-memory),
- interaction logs (`interaction_logs.json`),
- persisted events (`live_state_events.db`) via `chat_turn`.

On startup, API hydrates persisted events to restore session context signals.

Note: persisted events help recover recent runtime analytics context, but they are not a full long-term model-serving database.

---

## 12) What "constraints used when training the chatbot" means here

In this implementation, the tutor is **prompt-constrained at inference time**; there is no custom model fine-tuning code in this component.

So "training constraints" in practice are:

- system prompt constraints,
- output schema constraints,
- retrieval grounding constraints,
- policy gate constraints for mastery update,
- environment-based behavior controls (`TUTOR_BKT_POLICY`, `TUTOR_LLM_TEMPERATURE`).

---

## 13) Key environment variables

- `GROQ_API_KEY`: required for LLM calls.
- `TUTOR_BKT_POLICY`: `quiz_only` (default), `strict`, or `legacy`.
- `TUTOR_LLM_TEMPERATURE`: response variability control (default `0.35`, clamped in code).

BKT engine also has stabilization controls:

- `BKT_UPDATE_DAMPING`
- `BKT_EARLY_MASTERY_CAP`
- `BKT_EARLY_MASTERY_ATTEMPTS`
- `BKT_MAX_STEP_UP`
- `BKT_MAX_STEP_DOWN`

These are applied in `bkt_engine.py` and affect all `predict_update` calls (including tutor-driven ones when policy permits).

---

## 14) Practical summary for presentations

If you need one concise explanation:

- The chatbot is a Socratic, RAG-grounded tutor with strict JSON outputs.
- It adapts pedagogy by estimated mastery and adapts tone by frustration signals.
- It may update mastery from dialogue only when policy allows and score confidence is decisive.
- Ground-truth quiz submissions remain the authoritative mastery update path.
